# Аккаунты: готовый модуль для продолжения backend

Этот документ описывает модуль аккаунтов из PR #19, добавленный со стороны Самира. Позже Артём реализовал каталог и справочники в PR #21, а Самир подключил их к интерфейсу. По отдельному разрешению Самира также реализованы заявки, выдачи и возвраты в `backend/src/circulation`. Артём продолжает инвентаризации, файлы, статистику, управление пользователями, общий аудит и XLSX; готовые модули не дублировать.

## Уже работает

- Express + TypeScript strict, Prisma 6.19.3, PostgreSQL, миграция `202610200001_auth`, seed трёх ролей и тестовых аккаунтов.
- Регистрация преподавателя, вход, access JWT на 15 минут, refresh JWT на 7 дней с ротацией; выход отзывает сессию. Пароли — bcrypt с cost 12; ограничения длины учитывают предел bcrypt в 72 байта.
- Refresh хранится в HttpOnly cookie `inventory_refresh`, Path `/api/auth`, SameSite=Lax, Secure в production; в БД хранится SHA-256 токена. Access — только в памяти frontend. При перезагрузке страницы сессия восстанавливается через refresh.
- Профиль, смена пароля с проверкой текущего, восстановление по одноразовой ссылке на 30 минут. Смена/сброс пароля отзывают все сессии. Ссылки восстановления выводятся в лог сервера, как разрешено заданием; API не раскрывает наличие email и сам код.
- Сервер читает актуальную роль и блокировку из БД при каждом защищённом запросе. Клиентские ID и роли не принимаются при редактировании собственного профиля и регистрации.
- История собственных действий аккаунта; чтение списка пользователей только администратором с серверными поиском, фильтром роли, сортировкой и пагинацией. Создание, изменение ролей и блокировка через API ещё не реализованы.
- CORS на один точный origin, проверка Origin для изменяющих запросов, ограничение попыток доступа, валидация тела и единые ошибки. Нельзя отправлять cookie-запросы с другого origin.
- Общий Compose: PostgreSQL → backend → Nginx/frontend, проверки готовности, миграции и идемпотентный seed. Локальная база не публикует порт наружу.

## Контракт

Реальная OpenAPI 3-спецификация: `GET /api/openapi.json`; Swagger UI: `/api/docs/`. В dev API работает на 3001, frontend на 5173 проксирует `/api`. В Compose всё доступно через `http://127.0.0.1:8080`.

Готовые маршруты: POST `/auth/register`, `/auth/login`, `/auth/refresh`, `/auth/logout`, `/auth/forgot-password`, `/auth/reset-password`; GET/PATCH `/me`; PATCH `/me/password`; GET `/me/activity`; GET `/users` для admin. Все пути начинаются с `/api`.

Пользователь: `{id, name, email, role, isBlocked}`. Роли в API: `teacher`, `technician`, `admin`. Успешный отдельный объект — `{data: object}`, список — `{data: [], total, page, pageSize}`. Вход и refresh возвращают `{data: {accessToken}}` и устанавливают refresh cookie. Регистрация возвращает 201 без автоматического входа.

Для изменения пароля тело `{currentPassword, password}`; для сброса `{token, password}`. Для ручных запросов и тестов требуется заголовок `Origin`, совпадающий с `CLIENT_ORIGIN`. Swagger отправляет его автоматически из браузера.

## Что продолжает Артём

1. Использовать существующие `createApp`, `authenticate(service)`, `requireRoles(...)` и `res.locals.auth`; тип `CurrentUser` экспортируется из `backend/src/auth/controller.ts`. Подключать новые маршруты перед общим обработчиком 404. Вторую авторизацию параллельно не создавать.
2. Расширять Prisma-схему новыми миграциями, не переписывая применённые. После миграции `202610210001_circulation` есть 13 таблиц; связи многие ко многим реализованы через RequestItem и LoanItem.
3. Использовать уже добавленные поля `entityType`, `entityId`, `details` аудита для новых операций. `/me/activity` ограничен текущим пользователем и уже содержит его действия с каталогом.
4. Реализовать CRUD пользователей, смену роли, блокировку и защиту последнего администратора. Проверка блокировки при доступе уже есть, но API управления пользователями пока содержит только чтение.
5. Продолжить загрузки, инвентаризацию, статистику, общий аудит и XLSX. Атомарная выдача/возврат, серверные списки заявок и выдач, решения и отмена уже реализованы; актуальный контракт — OpenAPI.

Frontend `/account` и четыре раздела `/app` работают с настоящим API и общей навигацией. Отдельная демоверсия использует DemoProvider; её переключатель ролей не выдаёт серверные токены.

## Проверки

При передаче модуля аккаунтов были пройдены 4 unit-теста AuthService и 10 интеграционных тестов API на настоящей PostgreSQL. Покрытие строк `src/auth/service.ts` — 100%, ветвей — 97,67%. После добавления заявок и выдач полный прогон содержит 47 серверных тестов; результаты и область покрытия — в [testing-report.md](testing-report.md). Порог CI — не ниже 60% для каждого показателя.

Frontend после подключения заявок и выдач: 29 тестов Vitest и 14 сценариев Chromium, включая реальные аккаунты, каталог и комплектный цикл заявки/выдачи/возврата. Проверяется адаптивность 360–1920 px.

Серверные тесты требуют `DATABASE_URL` с именем отдельной БД, заканчивающимся на `_test`, и предварительного `prisma migrate deploy`. Они удаляют только собственные записи со случайным суффиксом. Unit-тесты запускаются без БД. Конфигурация test использует отдельные тестовые секреты; реальные `.env` и пароли не включаются в Git.

```sh
pnpm --dir backend lint
pnpm --dir backend format:check
pnpm --dir backend typecheck
pnpm --dir backend test
pnpm --dir backend build
```

Для локального запуска тестов с отдельным файлом переменных: из `backend` выполнить `node --env-file=.env.test node_modules/vitest/vitest.mjs run --coverage`. Для браузерных сценариев с API установить `RUN_API_TESTS=1` и запустить frontend e2e при работающем API.

В GitHub Actions добавлена проверка backend и браузерной интеграции с PostgreSQL, сборка и запуск всего Compose, затем проверка входа/профиля/выхода через Nginx. Docker на локальном компьютере не установлен; результат Compose подтверждается отдельным прогоном CI.
