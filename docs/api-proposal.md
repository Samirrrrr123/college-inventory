# API: предложение для согласования

Статус: аккаунты, оборудование, категории и аудитории уже реализованы; точный работающий контракт — `/api/openapi.json`, детали — [auth-handoff.md](auth-handoff.md) и [catalog-handoff.md](catalog-handoff.md). Лаборант и администратор изменяют все три сущности каталога, преподаватель только читает. Остальные предметные маршруты ниже остаются предложением для Артёма и не означают наличия серверной реализации. При расхождении этого черновика с работающим каталогом использовать OpenAPI.

Уточнение предметной области: календарное резервирование не требуется для темы учёта оборудования. Рекомендуемый вариант для интеграции — заявка на несколько конкретных единиц, выдача и возврат комплекта целиком. Доступность проверяется при фактической выдаче. Демонстрационный интерфейс уже поддерживает комплект; точные поля состава заявки/выдачи нужно получить из OpenAPI backend.

## Общие правила

- Базовый путь — `/api`. Идентификаторы передаются строками, даты событий — ISO 8601 с часовым поясом, даты без времени (если используются) — `YYYY-MM-DD`.
- Ключи JSON — camelCase. Роли: `teacher`, `technician`, `admin`. Названия и пользовательский текст хранятся без автоматического перевода; интерфейс переводит коды ролей и статусов.
- Поиск, фильтры, сортировка и пагинация выполняются сервером. Пример: `GET /api/equipment?page=1&pageSize=20&search=Epson&status=available&sort=name&order=asc`. Фильтры категории и аудитории — `categoryId`, `roomId`.
- Сервер ограничивает `pageSize` и разрешённые поля сортировки. `total` — число результатов после фильтрации, до разбиения на страницы.
- Успешный список возвращает `{ "data": [], "page": 1, "pageSize": 20, "total": 0 }`, отдельный объект — `{ "data": {} }`. Создание — HTTP 201, удаление без тела — 204.
- Ошибка: `{ "error": { "code": "VALIDATION_ERROR", "message": "Проверьте поля", "fields": { "inventoryNumber": "Уже используется" } } }`. `fields` необязательно. Нужны корректные HTTP 400/401/403/404/409/413/415/422/429/500.

## Основные объекты

| Объект         | Поля, необходимые интерфейсу                                                     |
| -------------- | -------------------------------------------------------------------------------- |
| Пользователь   | id, name, email, role, isBlocked                                                 |
| Категория      | id, name                                                                         |
| Аудитория      | id, number, name, building, floor                                                |
| Оборудование   | id, name, inventoryNumber, categoryId, roomId, status, description, attachmentId |
| Заявка         | id, number, requesterId, items (equipmentId), purpose, status, createdAt         |
| Выдача         | id, recipientId, requestId, items (equipmentId), issuedAt, dueAt, returnedAt     |
| Перемещение    | id, equipmentId, fromRoomId, toRoomId, actorId, createdAt                        |
| Инвентаризация | id, roomId, actorId, status, startedAt, completedAt; позиции: equipmentId, found |
| Вложение       | id, originalName, mimeType, size, downloadUrl                                    |
| Аудит          | id, actorId, action, entityType, entityId, createdAt                             |

Это поля для обмена данными, а не готовая схема БД. Связи, таблицы и миграции проектирует Артём. Для таблиц интерфейса API также должен отдавать отображаемые имена связанных объектов либо справочники. Пароль и его хеш в ответ пользователя не входят.

Статусы оборудования: `available`, `issued`, `repair`, `written_off`. Заявки: `pending`, `approved`, `rejected`, `cancelled`. Просрочка выдачи вычисляется по `dueAt`, если `returnedAt` отсутствует.

## Маршруты

| Раздел         | Предлагаемые запросы                                                                                                   |
| -------------- | ---------------------------------------------------------------------------------------------------------------------- |
| Доступ         | POST `/auth/register`, `/auth/login`, `/auth/refresh`, `/auth/logout`, `/auth/forgot-password`, `/auth/reset-password` |
| Профиль        | GET/PATCH `/me`, PATCH `/me/password`, GET `/me/activity`                                                              |
| Каталог        | GET/POST `/equipment`, GET/PATCH/DELETE `/equipment/{id}`                                                              |
| Справочники    | GET/POST `/categories`, `/rooms`; GET/PATCH/DELETE `/categories/{id}`, `/rooms/{id}`                                   |
| Заявки         | GET/POST `/requests`, GET `/requests/{id}`, POST `/requests/{id}/approve`, `/reject`, `/cancel`                        |
| Выдачи         | GET/POST `/loans`, GET `/loans/{id}`, POST `/loans/{id}/return`                                                        |
| Перемещения    | GET/POST `/movements`                                                                                                  |
| Инвентаризация | GET/POST `/inventory-checks`, GET/PATCH `/inventory-checks/{id}`, POST `/inventory-checks/{id}/complete`               |
| Пользователи   | GET/POST `/users`, GET/PATCH `/users/{id}`; изменение роли и блокировки через PATCH                                    |
| Вложения       | POST `/files` с multipart-полем `file`, GET/DELETE `/files/{id}`                                                       |
| Статистика     | GET `/dashboard`                                                                                                       |
| Дополнения     | GET `/audit`, GET `/equipment/export` с XLSX в теле и Content-Disposition                                              |

Начальный лимит файлов: JPG, PNG или PDF, до 5 МБ. Сервер проверяет размер, содержимое, права загрузки и скачивания. Непроверенный оригинальный файл не исполняется в браузере как страница.

## Доступ и бизнес-правила

- Преподаватель просматривает каталог и аудитории, создаёт и видит свои заявки, свои выдачи и профиль. Отменяет только свою ожидающую заявку.
- Лаборант ведёт оборудование, аудитории, заявки, выдачи, возвраты, перемещения и инвентаризации. Администратор дополнительно управляет категориями, пользователями, ролями и блокировками, видит общий аудит.
- Проверки роли и владельца ресурса выполняются на сервере при каждом запросе. Переключатель ролей в демонстрационном интерфейсе не участвует в авторизации.
- Заявка и её одобрение не резервируют оборудование. При фактической выдаче сервер проверяет доступность каждой единицы и защищает от одновременной выдачи одного предмета двум пользователям. Если хотя бы одна единица недоступна, весь комплект не выдаётся: частичного изменения данных не происходит.
- При выдаче фиксируется срок возврата. Выдача и возврат комплекта выполняются целиком; частичные выдачи и возвраты в эту версию не входят. Выдача, возврат и перемещение обновляют связанные данные в транзакции и попадают в аудит.
- Удаление оборудования с историей выдач, активными заявками или проверками возвращает конфликт; согласовать архивирование вместо потери истории.

## Что уточнить перед подключением

1. Совпадают ли поля, enum и маршруты с backend; способ выдачи связанных имён.
2. JWT access + refresh: предлагается держать access в памяти приложения, refresh в HttpOnly cookie, обновлять refresh при использовании и отзывать при выходе. Согласовать срок жизни, cookie/CORS и защиту от CSRF. Регистрация создаёт только преподавателя, не принимает произвольную роль от клиента.
3. Точные тела запросов и ответов, обязательность полей, разрешённые переходы статусов, состав статистики и поведение удаления справочников.
4. Реальный OpenAPI-файл и Swagger UI — источник утверждённого контракта. После согласования Артём описывает эти детали там, frontend подключается к ним.
