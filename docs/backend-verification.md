## Повторение тестов

Нужна отдельная PostgreSQL без заранее созданных активных администраторов: тесты сами создают и удаляют свои данные; тест последнего администратора требует изолированную базу. Имя БД должно оканчиваться на `_test`. Не применять тестовый env к обычному приложению.

Пример отдельной БД Docker, вне общего Compose проекта:

```sh
docker run --name inventory-api-test -e POSTGRES_USER=inventory -e POSTGRES_PASSWORD=local-test-only -e POSTGRES_DB=inventory_test -p 127.0.0.1:55432:5432 -d postgres:18-alpine
```

Дождаться готовности PostgreSQL. Из корня установить backend-зависимости и сгенерировать Prisma-клиент. Затем скопировать backend/.env.test.example в backend/.env.test. Значения примера предназначены только для локальных тестов.

Из backend:

```sh
node --env-file=.env.test node_modules/prisma/build/index.js migrate deploy
pnpm lint
pnpm format:check
pnpm typecheck
node --env-file=.env.test node_modules/vitest/vitest.mjs run --coverage
pnpm build
```

Если переменные уже заданы окружением CI, достаточно существующих pnpm generate, pnpm migrate, pnpm test. Команды test:coverage и test дают тот же полный прогон. test:unit выполняет unit-тесты без БД; test:integration выполняет API и seed-тесты с БД. Порог покрытия всех сервисов проверяет полный прогон, а не каждый отдельный набор.

Существующий backend workflow использует PostgreSQL 18, проверяет Docker Compose и браузерную интеграцию. Состояние проверок актуального коммита находится в Checks PR. Локально в этой итерации не заявляются запуск Docker, браузерный прогон или проверка публичного сайта; результаты CI фиксируются отдельно в PR.
