## Frontend и браузер

Подробный список локальных проверок интерфейса приведён в [frontend-testing.md](frontend-testing.md). Основные группы:

- Формы проверяют обязательные поля, email, совпадение паролей, уникальные значения справочников и понятные ошибки. Проверяются фокус, закрытие диалога и подтверждение удаления.
- Темы и RU/EN сохраняются; системная тема реагирует на настройки устройства. Шесть основных экранов и формы доступа не имеют горизонтального переполнения на проверенных ширинах.
- Демооперации проверяют комплектную заявку, одобрение, выдачу, изменение статусов каталога и возврат. Отдельный тест запрещает частичную выдачу, если один предмет занят. Это не проверка серверной транзакции выдачи.
- Реальные сценарии проверяют регистрацию, вход, сохранение профиля в БД, восстановление сессии после перезагрузки, выход и смену пароля. Проверяется, что refresh cookie имеет HttpOnly, а access и пароль отсутствуют в localStorage/sessionStorage.
- Тесты API-клиента проверяют одно обновление сессии для параллельных запросов, один повтор после истёкшего access и отказ без запроса данных при отозванном refresh.

## Как воспроизвести

Для frontend установить зависимости и выполнить `lint`, `format:check`, `typecheck`, `test`, `build` из его каталога. Для браузера установить Chromium и выполнить `test:e2e`. Для двух реальных сценариев аккаунтов дополнительно запустить backend и установить `RUN_API_TESTS=1`.

Для backend задать тестовые переменные окружения, включая URL отдельной PostgreSQL с окончанием `_test`, разные секреты JWT и точный origin frontend. Применить миграции к этой тестовой базе, затем выполнить `pnpm test`. В репозитории не публикуются реальные `.env`, токены или пароль локальных тестовых аккаунтов.

Общий запуск и тестовые роли описаны в [README](../README.md), поля и правила аккаунтов - в [auth-handoff.md](auth-handoff.md). Полный порядок CI зафиксирован в workflow-файлах репозитория.

## Что ещё предстоит проверить

Серверные CRUD оборудования и справочников, операции заявок/выдач/перемещений/инвентаризации, конкурентную выдачу в транзакции, доступ к вложениям, XLSX, статистику и аудит предметных операций нужно проверить после добавления API Артёма. Управление ролями и блокировкой через API также ещё не реализовано.

Итоговая БД команды с минимум 8 таблицами, связью многие ко многим и полной предметной ER-диаграммой пока не готова. Производительность типовых запросов менее 500 мс не измерялась. Публичный деплой и прохождение полного MVP с тремя ролями не подтверждаются текущим отчётом.

После интеграции документ дополняется фактическими результатами и экспортируется в PDF для сдачи. Это отчёт о текущем этапе, а не заключение о готовности всего проекта к защите.
