## Запуск и обновление

Стандартный запуск из корня не изменился:

```sh
node scripts/setup-env.mjs
docker compose up --build
```

Swagger: http://127.0.0.1:8080/api/docs/. Спецификация: http://127.0.0.1:8080/api/openapi.json. Базовый путь `/api`; в `paths` спецификации повторного `/api` нет. В отдельном dev-запуске backend — 3001, frontend — 5173. Авторизация, refresh cookie и Origin продолжают работать по существующему контракту.

Новых обязательных переменных окружения и volume нет. Файлы текущей реализации хранятся в PostgreSQL как Bytes; они сохраняются в существующем volume базы. ExcelJS 4.4.0 добавлен в backend/package.json и lockfile, серверный Dockerfile устанавливает его автоматически.

Новая миграция `202610210004_reporting_indexes` добавляет только индексы для аудита, перемещений и графика выдач. Применённые миграции не переписаны. При Compose-запуске миграции и обычный seed выполняются командой существующего backend-контейнера. Не удалять volume и не запускать reset.

При запуске без Docker после получения ветки:

```sh
pnpm --dir backend install --frozen-lockfile
pnpm --dir backend generate
```

Затем из backend, с локальным `.env` и доступной PostgreSQL:

```sh
node --env-file=.env node_modules/prisma/build/index.js migrate deploy
pnpm seed
pnpm dev
```

Тестовые аккаунты — admin@college.test, technician@college.test, teacher@college.test. Пароль берётся из локального SEED_PASSWORD; существующие хеши seed не заменяет.

## Необязательные данные для демонстрации

Обычный seed по-прежнему создаёт каталог из 36 предметов и не выдаёт существующую технику. После него можно один раз явно добавить отдельные учебные сценарии:

```sh
pnpm --dir backend seed:demo
```

В уже работающем Compose, где env передан контейнеру:

```sh
docker compose exec backend pnpm exec tsx prisma/demo-seed.ts
```

Будут добавлены отдельная категория, две аудитории, четыре предмета SCENARIO-1…4, четыре заявки, три выдачи (действующая, просроченная и возвращённая), перемещение и завершённая инвентаризация. Операции связаны с демонстрационными аккаунтами. Повторный запуск ничего не сбрасывает и не меняет отредактированные записи. Время первого запуска фиксируется; просрочка затем вычисляется по реальному времени. Это необязательные демонстрационные записи, а не действия реальных пользователей. Автоматически при обновлении сервера они не добавляются.

## Новые маршруты

Все требуют Bearer access JWT. POST/PATCH дополнительно требуют Origin, совпадающий с CLIENT_ORIGIN. Запросы и ответы со схемами, ограничениями, null, enum и кодами ошибок находятся в Swagger.

| Метод и путь              | Доступ           | Назначение                               |
| ------------------------- | ---------------- | ---------------------------------------- |
| GET /api/dashboard        | Все три роли     | Счётчики и график                        |
| GET /api/audit            | admin            | Общий журнал                             |
| GET /api/movements        | technician/admin | История перемещений                      |
| POST /api/movements       | technician/admin | Перемещение с причиной                   |
| GET /api/equipment/export | technician/admin | XLSX                                     |
| POST /api/users           | admin            | Создание аккаунта                        |
| GET /api/users/{id}       | admin            | Карточка пользователя                    |
| PATCH /api/users/{id}     | admin            | Имя/email в дополнение к роли/блокировке |

Списки возвращают `{data: [], total, page, pageSize}`; карточки — `{data: {}}`. Размер страницы — до 100. У аудита и перемещений порядок по умолчанию `createdAt desc`, при равенстве — `id asc`. Неизвестные параметры и поля отклоняются с 422. Ошибка имеет вид `{error: {code, message, fields?}}`.

### Дашборд

Пример структуры ответа:

```json
{
  "data": {
    "generatedAt": "2026-10-21T12:00:00.000Z",
    "scope": "own",
    "totalEquipment": 36,
    "equipmentByStatus": {
      "available": 32,
      "issued": 2,
      "repair": 1,
      "written_off": 1
    },
    "activeLoans": 1,
    "overdueLoans": 0,
    "pendingRequests": 1,
    "loansByDay": [
      { "date": "2026-10-15", "count": 0 },
      { "date": "2026-10-16", "count": 0 },
      { "date": "2026-10-17", "count": 0 },
      { "date": "2026-10-18", "count": 0 },
      { "date": "2026-10-19", "count": 0 },
      { "date": "2026-10-20", "count": 1 },
      { "date": "2026-10-21", "count": 0 }
    ]
  }
}
```

Цифры выше иллюстративные. У teacher `scope=own`: выдачи, просрочки, заявки и график только свои. У сотрудников `scope=all`. Счётчики оборудования общие для всех, как доступный всем каталог. overdueLoans входит в activeLoans. График считает выдачи, включая впоследствии возвращённые, за семь календарных дней UTC; дни без операций имеют ноль. Чужие имена и заявки преподавателю не возвращаются.

### Аудит и перемещения

Аудит: `search` по действию/имени автора, точные actorId/entityType/entityId/action, включительные from/to в ISO 8601 с часовым поясом, sort=createdAt/action, order, page/pageSize. from не должен быть позже to. В ответе есть actor `{id,name}`, объект операции и допустимые details; пароли, JWT, reset-токены и байты файлов не записываются.

Перемещения: `search` по причине, названию и инвентарному номеру; equipmentId/fromRoomId/toRoomId/actorId, from/to, sort=createdAt, order, page/pageSize. Ответ включает equipment, fromRoom, toRoom и actor с отображаемыми именами. Видна также история, созданная изменением roomId в карточке оборудования. Исторические записи не редактируются и не удаляются.

Пример тела POST /api/movements; UUID берутся из настоящих справочников:

```json
{
  "equipmentId": "00000000-0000-4000-8000-000000000101",
  "toRoomId": "00000000-0000-4000-8000-000000000201",
  "expectedFromRoomId": "00000000-0000-4000-8000-000000000202",
  "reason": "Перенос для учебного занятия"
}
```

expectedFromRoomId необязателен, но рекомендуется для защиты от устаревшей карточки. Изменение аудитории, Movement и AuditEntry сохраняются одной serializable-транзакцией с ограниченным повтором при конфликте. Выданный предмет сначала нужно вернуть. Одинаковая аудитория даёт 409 SAME_ROOM, устаревшая исходная — 409 CONCURRENT_CHANGE, отсутствующий объект — 404. Подмена ID и неуспешная операция не оставляют частичных изменений.

### XLSX

Пример: `GET /api/equipment/export?status=available&sort=name&order=asc`.

Поиск, categoryId/roomId/status и sort/order совпадают с каталогом. В выгрузку входят все найденные строки; page/pageSize здесь запрещены. Максимум 5000 строк: при превышении сервер возвращает 422 EXPORT_TOO_LARGE и предлагает сузить фильтры, вместо незаметного усечения. Пустой результат даёт файл с заголовками.

Content-Type: `application/vnd.openxmlformats-officedocument.spreadsheetml.sheet`. Content-Disposition: `attachment; filename="equipment-YYYY-MM-DD.xlsx"` с датой UTC. В интерфейсе ответ нужно получать как Blob, затем сохранять; текущий JSON-клиент для бинарного ответа не подходит. Успешная подготовка выборки записывается в аудит как equipmentExported с фильтрами и количеством строк; это не подтверждение, что браузер сохранил файл.

Лист содержит инвентарный номер, имя, категорию, корпус, аудиторию, статус, серийный номер и описание. Пользовательские значения записываются как строковые ячейки, без формул и гиперссылок. Проверено обратным чтением XLSX для строк, начинающихся с `=`, `+` и `@`. Используется [ExcelJS](https://github.com/exceljs/exceljs#value-types).

### Пользователи

POST /api/users принимает name, email, password, role и необязательный isBlocked=false. Роли те же: teacher/technician/admin. Пароль — 8–72 символа и не более 72 байт UTF-8. Email приводится к нижнему регистру; дубликат даёт 409 EMAIL_EXISTS. Пароль хешируется bcrypt, в ответе и аудите его нет; сессия созданному аккаунту не выдаётся.

PATCH принимает непустое подмножество name/email/role/isBlocked. Ответы содержат обычного публичного пользователя и isLastAdmin. Любое реальное изменение отзывает старые сессии и reset-коды целевого пользователя; no-op их сохраняет. Защита последнего активного администратора и повторная проверка прав автора в транзакции сохранены. Аккаунты блокируются вместо физического удаления, чтобы не терять историю.

## Проверки

Локально пройдены API-тесты с настоящей PostgreSQL 17.10, unit-тесты, линтер, TypeScript strict, сборка и валидация OpenAPI 3 (38 путей). Подробные итоговые числа и CI — в [проверке backend](backend-verification.md). PostgreSQL 18 и общий Docker/браузерный запуск проверяет существующий CI PR; локальный замер не заменяет эти проверки.

Минимальный сценарий интеграции для Самира: открыть Swagger, войти под каждой ролью, подключить GET dashboard, затем аудит admin, историю/создание перемещения staff и скачивание XLSX. Для новых полей формы пользователя использовать расширенные POST/PATCH; старые PATCH role/isBlocked продолжают работать.
