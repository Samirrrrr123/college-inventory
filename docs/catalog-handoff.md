# Каталог: передача для подключения frontend

Статус: реализован блок оборудования, категорий и аудиторий поверх авторизации из main (основа 3e44e41). Рабочая ветка: feat/catalog-api. Авторизация, cookie, роли и профиль продолжают использовать существующий модуль backend/src/auth; второй модуль не добавлялся.

## Запуск

Общий запуск остаётся тем же:

```sh
node scripts/setup-env.mjs
docker compose up --build
```

Миграции и seed запускаются существующим Compose. Добавлена миграция 202610200002_catalog; применённая 202610200001_auth не изменена. На уже работающем сервере после получения ветки выполнить pnpm --dir backend generate, затем миграцию через существующую команду запуска. Не использовать reset и не удалять volume БД.

Приложение доступно на http://127.0.0.1:8080, Swagger — http://127.0.0.1:8080/api/docs/, спецификация — http://127.0.0.1:8080/api/openapi.json. При отдельном dev-запуске backend остаётся на 3001, frontend на 5173 проксирует /api. Детали сессий — в auth-handoff.md.

Seed сохраняет существующие пароли и данные. При первом запуске создаёт 36 единиц оборудования, 3 категории и 3 аудитории. У оборудования номера DEMO-0001…DEMO-0036; есть состояния available, repair, written_off. Демоданные не содержат персональных сведений. Тестовые аккаунты те же: admin@college.test, technician@college.test, teacher@college.test; пароль берётся из локального SEED_PASSWORD и в Git не записывается.

## Права и формат

| Действие                          | teacher | technician | admin |
| --------------------------------- | ------- | ---------- | ----- |
| Читать списки и карточки          | Да      | Да         | Да    |
| Создавать, редактировать, удалять | Нет     | Да         | Да    |

Все маршруты требуют реального Bearer access JWT. Для POST/PATCH/DELETE нужен Origin, совпадающий с CLIENT_ORIGIN; браузер выставляет его при запросе. Демопереключатель ролей токен не выдаёт.

Идентификаторы — UUID. Роли API: teacher / technician / admin. Статусы оборудования: available / issued / repair / written_off. Интерфейс пока использует enum верхнего регистра — нужен адаптер. Для лаборанта соответствие technician → LAB_ASSISTANT, для ремонта repair → MAINTENANCE.

Ответ одного объекта: {data: object}. Список: {data: [], total, page, pageSize}. Создание возвращает 201, удаление — 204 без тела. Ошибки совместимы с авторизацией: {error: {code, message, fields?}}. Некорректные входные данные дают 422; нет входа — 401; нет прав — 403; объект отсутствует — 404; конфликт — 409.

## Маршруты

| Сущность     | Список и создание        | Карточка, изменение, удаление         |
| ------------ | ------------------------ | ------------------------------------- |
| Оборудование | GET/POST /api/equipment  | GET/PATCH/DELETE /api/equipment/{id}  |
| Категории    | GET/POST /api/categories | GET/PATCH/DELETE /api/categories/{id} |
| Аудитории    | GET/POST /api/rooms      | GET/PATCH/DELETE /api/rooms/{id}      |

Все списки поддерживают search, page (от 1), pageSize (1…100), sort, order (asc/desc). По умолчанию page=1, pageSize=20, order=asc. Дополнительный порядок по id обеспечивает стабильную пагинацию. total считается после фильтрации. Неизвестные параметры отклоняются, поисковая строка — максимум 200 символов. Для справочников более 100 записей нужно получать следующие страницы.

Оборудование: sort=name/inventoryNumber/status/createdAt/updatedAt (по умолчанию name); фильтры categoryId, roomId, status. Поиск без учёта регистра по name, inventoryNumber, serialNumber. Категории: sort=name, поиск по name. Аудитории: sort=number/name/building/floor (по умолчанию number), поиск по number/name/building; точные фильтры building и floor, в том числе floor=0.

Пример:

```http
GET /api/equipment?search=DEMO&status=available&sort=name&order=asc&page=1&pageSize=20
Authorization: Bearer <accessToken>
```

## Примеры тел

Создание категории:

```json
{ "name": "Ноутбуки" }
```

Создание аудитории:

```json
{
  "number": "301",
  "name": "Кабинет информатики",
  "building": "Главный корпус",
  "floor": 3
}
```

Создание оборудования: categoryId и roomId берутся из ответов справочников, а не из демоданных frontend.

```json
{
  "name": "Ноутбук учебный",
  "inventoryNumber": "INV-0042",
  "categoryId": "00000000-0000-4000-8000-000000000101",
  "roomId": "00000000-0000-4000-8000-000000000201",
  "serialNumber": null,
  "description": "Для учебных занятий",
  "status": "available"
}
```

serialNumber, description и status можно не передавать при создании; значения по умолчанию null, пустая строка и available. Название и номер оборудования обязательны. Инвентарный номер обрезается по краям и приводится к верхнему регистру перед сохранением; уникальность защищена индексом PostgreSQL, включая одновременные запросы.

PATCH принимает непустое подмножество редактируемых полей. Отсутствующие поля сохраняются, значения по умолчанию повторно не применяются:

```json
{ "name": "Новое название" }
```

Ответ оборудования содержит все его скалярные поля, createdAt/updatedAt в ISO 8601, вложенные category и room для отображения имён. attachmentId пока всегда null: загрузки файлов будут отдельным этапом. У категорий поля id/name; у аудиторий id/number/name/building/floor. Локализованные title/location из демомодели frontend нужно заменить адаптером на эти данные; пользовательские названия сервер не переводит.

Пример конфликта:

```json
{
  "error": {
    "code": "INVENTORY_NUMBER_EXISTS",
    "message": "This value is already in use",
    "fields": { "inventoryNumber": "Already in use" }
  }
}
```

Коды конфликтов: INVENTORY_NUMBER_EXISTS, ALREADY_EXISTS, RELATED_RECORDS, EQUIPMENT_ISSUED, CONCURRENT_CHANGE. При CONCURRENT_CHANGE пользователь может повторить действие.

## История и удаление

- Удаление пустой категории/аудитории и оборудования без связанных операций выполняется физически.
- PostgreSQL запрещает удаление справочников, на которые ссылаются оборудование или история перемещений; API возвращает 409 RELATED_RECORDS.
- Смена roomId через PATCH оборудования создаёт Movement и запись аудита в той же транзакции. Если новая аудитория не существует, обновление, перемещение и аудит откатываются вместе.
- Оборудование с историей перемещений удалить нельзя. Старые исходные аудитории также защищены от удаления.
- issued нельзя назначить через создание или PATCH. Для реально выданного оборудования запрещены удаление, смена статуса и аудитории; название и описание редактировать можно. Выдача/возврат появятся следующим блоком.
- Записи каталога попадают в существующий аудит с actorId/action/entityType/entityId/details. История /me/activity по-прежнему ограничена текущим пользователем. Общий журнал аудита будет отдельным этапом.

## Проверки

Результаты и условия находятся в catalog-testing.md. Пройдены 39 тестов, включая существующую авторизацию и API каталога на настоящей PostgreSQL. OpenAPI проверен валидатором. Миграция проверена с нуля и поверх прежней схемы с существующим пользователем, хешем пароля и аудитом. Seed запущен дважды.

Frontend, общий Compose и CI в этом PR не менялись. Существующий backend workflow автоматически запускает новые тесты и распространяет порог покрытия на все service.ts в src. Локальная проверка API выполнена на PostgreSQL 17.10; общий Compose/CI использует PostgreSQL 18. Результат Docker-сборки и CI нужно смотреть отдельно в GitHub Actions после публикации.
