# Передача frontend для интеграции

## Текущий этап

React-интерфейс по макетам Figma, шесть разделов, адаптивная вёрстка, светлая/тёмная/системная тема, RU/EN. Настройки интерфейса сохраняются в localStorage; персональные данные и токены туда не записываются.

Шесть основных разделов пока работают в явно обозначенном демонстрационном режиме. Начальный пользователь — Самир. Внизу страницы можно переключить пример на Артёма или преподавателя. Это просмотр интерфейса, а не аутентификация и не реализация серверного RBAC. Отдельная страница `/account` уже подключена к настоящему API и PostgreSQL; демоданные и реальные аккаунты не смешиваются.

Формы доступа `/login`, `/register`, `/forgot-password`, `/reset-password?token=…` выполняют реальные запросы. После входа открывается `/account`: профиль, смена пароля, собственная история, выход. Есть проверка полей, состояния ожидания и понятные ошибки RU/EN. Access хранится в памяти, refresh — в HttpOnly cookie; пароль не попадает в хранилища и очищается после отправки. Срок и одноразовость ссылки восстановления проверяет сервер. Детали — в [auth-handoff.md](auth-handoff.md).

Демооперации действуют в памяти до перезагрузки страницы: создание/редактирование/удаление оборудования, аудиторий и категорий; добавление/изменение пользователей, роли и блокировка; заявки из нескольких предметов, решения по заявкам, выдача и возврат целого комплекта; перемещение, проверка наличия и редактирование профиля. Есть проверки уникальности email, номера аудитории и названия категории, запрет отключения последнего администратора и удаления связанных с историей справочников. Проверки демонстрируют поведение формы; сервер обязан заново проверять все правила.

Поиск, сортировка, фильтры и пагинация в основных шести разделах пока локальные. Выбор файла проверяет тип/размер в браузере и показывает имя, но файл не отправляется и не сохраняется на сервере. Экспорт и операции с оборудованием требуют предметного API Артёма. Смена пароля в демопрофиле явно недоступна; в настоящем `/account` она обращается к серверу, проверяет текущий пароль и отзывает все сессии.

## Структура

- `frontend/src/app` — маршруты, оболочка, настройки интерфейса.
- `frontend/src/components` — кнопки, поля, диалоги, статусы, вкладки и пагинация.
- `frontend/src/features` — каталог с формами и настройки темы/языка.
- `frontend/src/features/auth` — оболочка форм доступа, общая валидация и поле пароля.
- `frontend/src/features/directories`, `people`, `requests` — формы справочников/пользователей, выбор комплекта, создание заявки и выдача.
- `frontend/src/pages` — остальные разделы.
- `frontend/src/domain/types.ts` — модели отображения frontend, ещё не утверждённый API-контракт.
- `frontend/src/demo` — тестовые данные и временные операции; заменяются интеграцией API.
- `frontend/src/i18n/messages.ts` — типизированные пары RU/EN.
- `frontend/public/icons` — оригинальные SVG из Figma, без временных сетевых ссылок.

## Что нужно согласовать с Артёмом

Отправная точка — [черновик API](api-proposal.md). Он не заменяет утверждённую OpenAPI-спецификацию и не обязывает переделывать уже написанный backend без обсуждения.

1. Расширение готовой OpenAPI-спецификации аккаунтов маршрутами предметной области.
2. Идентификаторы, поля оборудования/аудиторий/категорий и enum статусов.
3. Формат списка: данные, номер/размер страницы, общее число; параметры поиска, фильтров и сортировки.
4. Использование уже готовых middleware авторизации и ролей, полей пользователей и сессий.
5. Правила доступа, обработки заявок, выдач, возвратов и перемещений.
6. Единые коды ошибок и ошибки полей. Перевод кодов и статусов делается на frontend, пользовательский текст автоматически не переводится.
7. Multipart-загрузку, ограничения файлов, идентификатор/URL вложения, проверку прав скачивания.
8. Метрики дашборда, аудит и бинарный XLSX с заголовком имени файла.
9. Расширение общего Compose и конфигурации backend при добавлении хранилища файлов и остальных сервисов.

После согласования интеграция заменит DemoProvider запросами к серверу. Не переносить демоданные в production и не считать скрытие кнопок защитой данных.

Интерфейс заявок подготовлен для варианта без календарной брони: несколько единиц в заявке, цель использования, выдача и возврат комплекта целиком. Одобрение не резервирует технику; выдать занятый предмет нельзя. Если недоступен хотя бы один предмет, весь комплект остаётся невыданным. Срок возврата задаётся при выдаче. Утверждённые поля и статусы всё равно берутся из OpenAPI backend; demo-модели не являются серверным контрактом.

История профиля привязана к `actorId`, поэтому смена имени не скрывает предыдущие действия. Подпись автора в аудите сохраняется на момент операции.

## Запуск и проверки

Сценарии и результаты локального прогона перечислены в [отчёте о проверках frontend](frontend-testing.md).

Нужны Node.js 24 и pnpm 11.25.0. Выполнять из корня репозитория:

```sh
pnpm --dir frontend install --frozen-lockfile
pnpm --dir frontend dev
pnpm --dir frontend lint
pnpm --dir frontend format:check
pnpm --dir frontend typecheck
pnpm --dir frontend test
pnpm --dir frontend build
pnpm --dir frontend exec playwright install chromium
pnpm --dir frontend test:e2e
```

Dev-сервер: http://127.0.0.1:5173. Команда e2e сама запускает dev-сервер; в CI на этом порту не должен одновременно работать другой сервер.

Dockerfile принимает контекст `frontend/`, отдаёт SPA через Nginx на 8080, healthcheck — `/health`. `/api/` перенаправляется на `backend:3001`. Общий `compose.yaml` поднимает PostgreSQL, API аккаунтов и frontend.

Workflow `Frontend` проверяет линтер/формат/типы, компоненты, демонстрационные браузерные сценарии и сборку SPA/Docker. Workflow `Backend and integration` проверяет API с PostgreSQL, покрытие текущего сервиса, реальные сценарии аккаунтов и запуск Compose. Успех конкретного запуска проверяется в GitHub Actions; новые сервисы и их тесты Артём добавляет в эти проверки.

Обязательное одобрение PR отключено по просьбе Самира. Проверенные изменения можно публиковать без ожидания второго участника; фактическое командное ревью остаётся отдельным пунктом задания, его не отмечать выполненным автоматически.

Комментарии в исходном коде и конфигурациях не добавляются по просьбе Самира; объяснения размещаются в документации.
