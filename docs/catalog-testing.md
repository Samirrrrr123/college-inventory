## Новые API-сценарии

1. Анонимный доступ запрещён; teacher читает, но не создаёт/изменяет/удаляет; technician/admin имеют права записи.
2. Полный CRUD оборудования; PATCH одного поля не стирает description, serialNumber, status или roomId; аудит фиксирует действия.
3. Нормализация инвентарного номера и конфликты создания/редактирования с ошибкой конкретного поля.
4. Два одновременных создания с одним номером дают 201 и 409, в БД одна запись.
5. Удаление связанных категории/аудитории запрещено; неверный внешний ключ не оставляет оборудование.
6. Смена аудитории создаёт историю; связанные удаления запрещены; неудачное перемещение откатывает данные и аудит.
7. Защита выданных единиц и запрет ручного присваивания issued.
8. Реальный состав поиска, фильтров, сортировки и двух страниц; стабильный порядок при одинаковых названиях; поиск серийного номера.
9. Неверные UUID, пустые PATCH, неизвестные поля, неподдерживаемые фильтры/сортировки и лимиты отклоняются; строка поиска не исполняется как SQL.
10. Полный CRUD категории и её уникальность.
11. Полный CRUD аудитории, уникальность building/number и фильтрация этажа.
12. Свой аудит, наличие каталога в Swagger и запрет стороннего Origin.
13. Воспроизводимые 36 демозаписей и сохранение существующих изменений повторным seed.

## Воспроизведение

Из backend при подготовленном локальном .env.test:

```sh
pnpm generate
pnpm migrate
pnpm lint
pnpm format:check
pnpm typecheck
node --env-file=.env.test node_modules/vitest/vitest.mjs run --coverage
pnpm build
```

Для migrate/test в окружении должен быть именно адрес тестовой БД; обычный .env не использовать для очистки тестовых данных. В CI эти переменные уже заданы существующим workflow. Реальные пароли и локальный .env.test в Git не включаются.

## Реально исправленные замечания при разработке

- Схемы PATCH отделены от схем создания: значения по умолчанию не должны сбрасывать пропущенные поля.
- Каталог подключается с аутентификацией только своих путей, чтобы не блокировать публичные маршруты входа и не проверять сессию дважды.
- Конфликты уникальности каталога переводятся в собственные коды и fields, а не в ранее существующий EMAIL_EXISTS.
- Смена аудитории сохраняет историю транзакционно; исторические внешние ключи запрещают бесследное удаление.

## Совместимость с PostgreSQL 18

Первый прогон GitHub Actions нашёл два ответа 500 вместо 409 при удалении связанных записей: Prisma 6 возвращала неизвестную ошибку для запрета RESTRICT на PostgreSQL 18. Добавлена отдельная миграция 202610200003_catalog_fk_compatibility, не переписывающая ранее применённые миграции. Ссылки каталога используют ON DELETE NO ACTION NOT DEFERRABLE INITIALLY IMMEDIATE: PostgreSQL продолжает немедленно запрещать удаление связанных строк, а Prisma обрабатывает его как P2003. Откладываемых ограничений и каскадного удаления нет. Исходные API-тесты сохраняют ожидание 409 и повторно запускаются на PostgreSQL 18 в CI.

Описание действий внешнего ключа: [документация Prisma 6](https://www.prisma.io/docs/orm/v6/prisma-schema/data-model/relations/referential-actions), [ограничения PostgreSQL](https://www.postgresql.org/docs/current/ddl-constraints.html).
