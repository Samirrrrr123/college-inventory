## Контракт списков

Оба запроса требуют Bearer access JWT и возвращают `{data: [], total, page, pageSize}`. page начинается с 1, максимум 100000; pageSize — 1–100, по умолчанию 20. Интерфейс запрашивает 10 строк. total считается после фильтрации. Порядок по умолчанию createdAt desc, при равенстве — id asc; список и total читаются в одной repeatable-read транзакции.

Общие параметры: search (до 200 символов), actorId (UUID), actorSearch (имя автора, до 100 символов), from/to (ISO 8601 с часовым поясом, включительно), order=asc/desc, page/pageSize. Все фильтры соединяются через AND. from не может быть позже to. Неизвестные параметры, неправильные UUID, размеры страницы и даты дают 422 VALIDATION_ERROR; без сессии — 401, без роли — 403. Ошибки сохраняют общий формат `{error: {code, message, fields?}}`.

### Перемещения

search ищет без учёта регистра по названию оборудования, инвентарному номеру и причине. Дополнительные точные фильтры: equipmentId/fromRoomId/toRoomId; sort допускает только createdAt. Данные создаются существующим PATCH roomId в карточке оборудования, как в main. Новые POST/PATCH/DELETE для истории не добавлены.

### Общий журнал

search ищет по имени автора или коду действия. Дополнительные точные фильтры: entityId, entityType, action; sort=createdAt/action. Специальный entityType=account выбирает прежние события аккаунта с entityType=null. Заблокированные авторы остаются в журнале и доступны поиску.

```http
GET /api/audit?entityType=equipment&action=equipmentUpdated&page=1&pageSize=10
Authorization: Bearer <accessToken>
```

Строка содержит id, actorId, actor `{id,name}`, action, entityType/entityId (могут быть null), details (объект или null), subject (строка или null), createdAt. subject — текущее отображаемое имя/номер оборудования, аудитории, категории, пользователя, заявки, выдачи или инвентаризации; это не исторический снимок названия. Для прежних событий аккаунта используется имя автора. Для удалённого/неизвестного объекта subject=null; интерфейс показывает пояснение и entityId, чтобы различать записи.

Пример строки внутри data:

```json
{
  "id": "00000000-0000-4000-8000-000000000006",
  "actorId": "00000000-0000-4000-8000-000000000005",
  "actor": { "id": "00000000-0000-4000-8000-000000000005", "name": "Лаборант" },
  "action": "equipmentUpdated",
  "entityType": "equipment",
  "entityId": "00000000-0000-4000-8000-000000000002",
  "details": {
    "changes": { "roomId": "00000000-0000-4000-8000-000000000004" },
    "previous": {
      "roomId": "00000000-0000-4000-8000-000000000003",
      "status": "available"
    }
  },
  "subject": "INV-0042 · Монитор",
  "createdAt": "2026-10-21T12:00:00.000Z"
}
```

Пароли, хеши, JWT, reset-коды, сессии и байты файлов не выбираются из связанных объектов. details берутся из уже существующих безопасных записей аудита. Чтение журналов не создаёт дополнительных событий и не меняет данные.

## Интерфейс и проверка

Использованы существующие компоненты, API-клиент, обновление сессии и состояния загрузки/ошибки. При смене фильтра страница сбрасывается на первую; доступны повтор запроса, обновление списка, сброс фильтров и пустой результат. Даты фильтров покрывают целые сутки UTC, время в таблицах также помечено UTC. Неверный интервал показывается в интерфейсе без отправки на сервер. Сведения аудита раскрываются как текст, без исполнения HTML.

Проверены RU/EN, светлая/тёмная темы, ширины 360/768/1440/1920. Отчёт с командами и точными результатами: [history-testing.md](history-testing.md).

Сценарий для ревью: под technician изменить аудиторию предмета в каталоге, открыть Перемещения и найти его по номеру, проверить исходную/новую аудиторию и автора. Под admin открыть Журнал аудита, выбрать тип Оборудование и действие Оборудование изменено. Под teacher убедиться, что обоих пунктов нет в меню и прямые адреса недоступны. Затем проверить фильтры, следующую страницу, пустой поиск и повтор после ошибки сети.
